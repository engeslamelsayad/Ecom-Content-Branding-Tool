## 2. القرارات المعمارية

### أ. الـ Skills تفضل Markdown — الأداة بتقراها وقت التشغيل

أهم قرار في المشروع. الاستراتيچية مش منسوخة في كود.

```
تعدّل ملف .md على GitHub → redeploy → الأداة بقت أذكى
                                       (من غير سطر كود واحد)
```

وتقدر تضيف skill رابعة (SEO، Retention، Email) بمجرد رفع فولدر جديد.

### ب. Progressive Disclosure + Prompt Caching

مش بنبعت الـ 3,700 سطر كل مرة. كل موديول بيحمّل `SKILL.md` بتاعه + الـ references اللي محتاجها **بس**. والبرومبت مرتّب عشان الكاش (الكاش بيطابق البادئة — أي بايت بيتحرك بيلغي كل اللي وراه):

```
system[0] = نص الـ skill          ← ثابت لكل موديول   (cached)
system[1] = القواعد + Brand Brain  ← ثابت لكل براند    (cached)
messages  = الطلب نفسه             ← متغيّر، مش متكاش
```

### ج. Brand Brain — الذاكرة الدائمة

**المشكلة:** الـ 3 skills كلهم بيقولوا حرفيًا *"Never skip the intake questionnaire"*. في داشبورد ده معناه إنك تجاوب على نفس الـ 8 أسئلة كل مرة تفتح موديول. بعد تلات مرات هتبطل تستخدمها.

**الحل:** طبقة ذاكرة لكل براند:

```
Brand ──┬── Identity      (الاسم · المجال · السوق · اللهجة)
        ├── Products      (السعر · التكلفة · الـ USP)
        ├── Avatars       (الرغبة · الخوف · الـ Trigger · الاعتراضات)
        ├── Competitors   (الرسالة · السعر · نقطة الضعف)
        ├── VoC Bank      (كلام عملاء حقيقي، بيدخل الكوبي بالحرف)
        └── Core          (مخرجات الموديولات السابقة)
```

كل موديول **بيقرأ** من الـ Brain. و11 موديول مخرجاتهم **بتدخل** الـ Brain — **بعد ما تعتمدها** (التفاصيل في القسم 12). تعمل `/heart` وتعتمده → القيم والأركيتايب يتخزنوا → أي موديول بعده يطلع متسق معاهم.

> ⚠️ في النسخة الأولى كانت المخرجات بتدخل الـ Brain لوحدها. ده اتغيّر في كوميت `ff626ba`: المخرج دلوقتي مسودّة لحد ما يتعتمد.

## 4. المساعد الذكي في الفورمات

**النقطة الحرجة:** خطة مبنية على إيراد متخيّل ومنافسين موهومين **بتحلل خيال — بثقة**. ده أسوأ من فورم فاضي.

فكل حقل بياخد سياسة:

| السياسة | العدد | المسموح | أمثلة |
|---|---|---|---|
| 🔒 `none` | 20 | **بيرفض** ويقولك تحط إيه | الميزانية · الإيراد · الهامش · الريفيوهات · روابطك · ذوقك |
| 📥 `extract` | 43 | بيسحبها من الـ Brain أو من مصدر انت دّيته | المنتج · اللهجة · الأسواق · العرض |
| ✍️ `draft` | 52 | بيقترح مسودّة من السياق | المشكلة اللي بتحلها · الإحساس المطلوب · صياغة الهدف |

**القاعدة متطبّقة في الكود مش في البرومبت.** ✅ *مُختبر:* خلّينا الموديل يخترع رقم إيراد بثقة `high` — السيرفر شال القيمة وحوّلها لـ `needs_user` قبل ما توصل للمتصفح، ورمى حقل مكنش مطلوب.

**شكل الاقتراح:** القيمة بتنزل في الحقل نفسه (تعدّلها على طول)، وتحتها درجة ثقة + مصدر الاقتراح + زرار رجوع. أول ما تعدّل، العلامة تختفي — بقت قيمتك.

## 5. التهيئة السريعة من رابط الموقع

في **نفس شاشة إنشاء البراند**:

```
+ براند جديد
  🌐 عندك موقع؟  https://yourstore.com  [🪄 اقرا]
        ↓
  Chromium يقرا لحد 5 صفحات (مش الرئيسية بس)
        ↓
  الاسم · الوصف · المجال · اللهجة  ← اتملوا
  + المنتجات والأسعار · المنافسين · الريفيوهات · الأفاتارات
        ↓
  تشيل الغلط → [أنشئ البراند واحفظ المحدّد]
```

**ترتيب الصفحات:** صفحات المنتجات والريفيوهات الأول (الأسعار والريفيوهات الحقيقية مش في الهوم بيدج)، بعدين "من نحن" والـ FAQ. نفس الدومين بس.

**الصندوق الأصفر** بيقولك إيه الناقص اللي لازم تحطه بنفسك (تكلفة المنتج، أرقام الأداء، باقي المنافسين).

### 🔒 ثغرة أمنية اتقفلت

السيرفر بقى بيفتح روابط اليوزر — دي **SSRF**. `assert_public_url()` بيفحص قبل الفتح **وبعد أي redirect**:

| الرابط | النتيجة |
|---|---|
| `http://169.254.169.254/` (بيانات السحابة) | ✅ اترفض |
| `http://localhost:8000/` · `http://127.0.0.1/` · `http://[::1]/` | ✅ اترفض |
| `https://10.0.0.5/` | ✅ اترفض |
| `file:///etc/passwd` | ✅ اترفض |
| `https://example.com` | ✅ اتقبل |

كلهم متأكد منهم **من خلال الـ API نفسه**.

## 6. المشاكل اللي حصلت وإزاي اتحلت

### ❌ 1. فشل بناء الـ Docker على Railway

```
BEWARE: your OS is not officially supported by Playwright;
        installing dependencies for ubuntu20.04-x64 as a fallback.
E: Package 'ttf-unifont' has no installation candidate
```

**السبب:** `python:3.12-slim` **بقى Debian 13 (trixie)** مش bookworm. Playwright 1.49 معندهوش قائمة اعتماديات لـ trixie → وقع على fallback بتاع ubuntu20.04 اللي فيه حزمتين خطوط مش موجودين في Debian.

**التحقق:** فتحت جدول Playwright الداخلي — `debian12` موجود (7 مواضع)، `trixie` **صفر**، و`ttf-unifont` في بلوك ubuntu20.04 بالظبط.

**الحل:** `FROM python:3.12-slim-bookworm` + تعليق يشرح ليه عشان محدش "ينضّفه".

---

### ❌ 2. `SECRET_KEY` كان إعداد ميت

كتبت في الـ README إنه مطلوب — **ومحدش كان بيقراه**. نظام الجلسات مابيحتاجوش:

| الطريقة اللي بتحتاجه | اللي عملناه |
|---|---|
| كوكي بتحمل بيانات **موقّعة** | كوكي بتحمل **توكن عشوائي** |
| لو المفتاح اتسرب → أي حد يزوّر جلسة | مفيش مفتاح يتسرب أصلاً |

اتشال هو ومكتبة `itsdangerous` اللي كانت مضافة عشانه.

### ❌ 3. صفحة بيضا بعد تسجيل الدخول (باج مني)

التعديل اللي كان المفروض يضيف `Globe, Wand2` للـ imports **مانفّذش**، وماتحققتش — اكتفيت إن البيلد نجح.

**الخطورة:** Vite مابيفشلش على اسم مش متعرّف — بيفترض إنه متغير عام ويبني عادي.

```
Shell بيترندر → NewBrandModal بيترندر (حتى والنافذة مقفولة،
لأن الـ JSX children بتتبني قبل ما تتبعت) → <Globe/> → ReferenceError
→ React بيفضّي الشجرة → صفحة بيضا
```

**إزاي اتعرف:** اللوج بتاعك كان بيقول كل حاجة —
```
POST /api/auth/login  200 OK
(مفيش /api/catalog ... مفيش حاجة خالص)
```
الوقوع حصل **أثناء الرندر**، قبل أي طلب. شغّلنا نسخة محلية بنفس البيلد المنشور وفتحناها بـ Chromium → نفس البصمة بالحرف.

**المنع:** ربطنا ESLint بالبيلد. وهنا درس مهم — أول ما ضفنا `no-undef` **جربنا نرجّع الباج للتأكد** وطلع الـ lint **خرج بـ 0**! لأن قواعد ESLint الأساسية مابتعتبرش اسم الكمبوننت في الـ JSX مرجع متغير. فضفنا `react/jsx-no-undef`:

```
src/App.jsx
  350:14  error  'Globe' is not defined  react/jsx-no-undef   exit=1
```

دلوقتي `npm run build` = `eslint src && vite build` — نسيان import بيفشّل البناء بدل ما يطلع صفحة بيضا.

## 12. تحديث: إزاي المخرجات بتأثر على اللي بعدها

### السؤال
لما أملا الـ Brand Brain والمكتبة، هل ده بيحسّن المخرجات اللي بعد كده؟

### الإجابة

**الـ Brand Brain: أيوه، بيأثر على كل مخرج.** **المكتبة: لأ**، الأداة مش بتقراها. بس فيه
11 موديول مخرجاتهم بتدخل الـ Brain **لما تعتمدها**.

| المصدر | بيوصل للموديل في كل تشغيلة؟ |
|---|---|
| هوية البراند (الاسم، المجال، السوق، اللهجة) | ✅ دايمًا |
| المنتجات بأسعارها وهامشها | ✅ دايمًا |
| الأفاتارات · المنافسين | ✅ دايمًا |
| بنك كلام العملاء (VoC) | ✅ دايمًا، والموديل بيستخدمه بالحرف |
| المخرجات **المعتمدة** من الـ 11 موديول | ✅ تحت عنوان "استراتيچية معتمدة — التزم بيها" |
| مسودات لسه ماتعتمدتش | ❌ |
| باقي المكتبة | ❌ متخزنة بس |

**الـ 11 موديول:**
- **Branding:** Discovery · Heart · Verbal · Positioning · Visual · Touchpoints · Architecture
- **Content:** VoC Mining
- **Marketing:** Onboarding · Full Plan · STPD

### نظام الاعتماد (كوميت `ff626ba`)

- أي مخرج بيطلع **مسودّة**، ومابيدخلش الـ Brain لوحده
- الحالات: `مسودة` → `مراجعة داخلية` → `مراجعة العميل` → `معتمد`
- زرار **"معتمد"** بيظهر للـ admin بس
- الاعتماد بيحفظ النسخة القديمة من الـ Brain قبل ما يستبدلها (`CoreRevision`)
- الموديول بيحفظ **آخر نسخة معتمدة بس**. لو اعتمدت Positioning جديد، بيحل محل القديم
- تقدر تمسح أي بند من الـ Brain من تاب Brand Brain

### الترتيب العملي

```
1. املا الـ Brain (أو "اقرا" من الموقع)
2. Branding    ← Heart → Verbal → Positioning   ← واعتمد كل واحد
3. Marketing   ← STPD أو Full Plan              ← واعتمده
4. Content     ← هنا بيطلع أحسن ما عنده
```

لو ماعتمدتش Positioning، الهوكات والسكريبتات اللي بعده مش هتعرف عنه حاجة.

**التكلفة:** الخطة الكاملة (13 قسم) طويلة. بعد ما تعتمدها، كل تشغيلة بتشيلها معاها في الـ
context، فالتكلفة بتعلى شوية. الكاش بيخفف الجزء الأكبر منه.

### ❌ تصحيح: باج "إعادة توليد قسم" ماكانش موجود في النسخة الحالية

قلتلك إن إعادة توليد قسم واحد من الخطة بتمسح باقي الخطة من الـ Brain وتسيب القسم الجديد
بس. **ده كان صح على نسخة قديمة بس**: اختبرته على `1786023` من غير ما أسحب آخر تحديثات من
GitHub. لما سحبت `main`، لقيت إن `ff626ba` كان صلّحها بالفعل، فماعملتش أي تعديل.

السيناريو على الكود الحالي:

| الخطوة | الـ Brain |
|---|---|
| 1. الخطة الكاملة خلصت، ولسه ماتعتمدتش | فاضي |
| 2. اعتمدت الخطة | 13 قسم ✅ |
| 3. أعدت توليد قسم STPD | لسه 13 قسم ✅ (في النسخة القديمة كانت بتبقى قسم واحد) |
| 4. اعتمدت القسم الفرعي لوحده | ماتغيرش ✅ |

**الدرس:** لازم أسحب آخر نسخة من الريبو قبل ما أختبر أو أبلّغ عن باج.

## 13. تحديث: موديول Product Guidelines

### الطلب
نقطة جديدة في قايمة الـ Content: الإرشادات اللي الكرييتور أو الـ UGC creator لازم يعرفها قبل ما
يصوّر فيديو للمنتج. اللي لازم يتقال، واللي ممنوع يتقال (زي أي حاجة بتتعارض مع صورة البراند)،
وأهم المميزات، والمنافع اللي هتعود على العميل. وبعدين اتطلب كمان إضافة أفضل الزوايا المرشحة
للكونتنت، وجنب كل زاوية مرحلة الوعي اللي بتخاطبها.

### البريف فيه إيه
أول كارت في الـ Content، لأن السكريبتات والمراجعات بتعتمد عليه. 9 أقسام:

| # | القسم | التفاصيل |
|---|---|---|
| 1 | المنتج في سطرين | كلام بسيط الكرييتور يقدر يقوله قدام الكاميرا |
| 2 | ✅ لازم يتقال | مرتّبة، وكل نقطة معاها ليه مهمة وإزاي تتقال باللهجة |
| 3 | ⛔ ممنوع يتقال | السبب + صياغة بديلة آمنة (تعارض مع صورة البراند، ادعاء طبي، نتايج مضمونة، ذكر منافس، وعد بسعر) |
| 4 | المميزات والمنافع | جدول الميزة ← الأفضلية ← المنفعة + المنافع العملية والعاطفية |
| 5 | الادعاءات المسموحة | المثبتة بس، والباقي «يحتاج إثبات» |
| 6 | **أفضل الزوايا المرشحة** | 4–6 زوايا، كل واحدة جنبها **مرحلة الوعي** (Schwartz 1–5) وليه، والفورمات، وجملة افتتاحية. 3 مراحل مختلفة على الأقل |
| 7 | توجيهات التصوير | اللقطات الإجبارية، نطق اسم البراند، النبرة |
| 8 | الـ CTA المعتمد | أساسي + بديل |
| 9 | Checklist قبل النشر | لمراجعة فيديو الكرييتور |

**الحقول:** المنتج (لازم يكون موجود في الـ Brain) · اللهجة · نوع الكرييتور · نقاط لازم تتذكر ·
ممنوعات تعرفها · ادعاءات مثبتة 🔒 · ملاحظات. حقل «ادعاءات مثبتة» سياسته `none`، يعني مساعد
الـ AI مش هيخترع فيه شهادات أو أرقام.

### إزاي بتتحفظ وبتتستخدم
- **لكل منتج لوحده:** بعد الاعتماد بتتحفظ في `Brand.core["product_guidelines"]` مقسّمة بالـ id
  بتاع المنتج، فإرشادات منتج مابتمسحش إرشادات منتج تاني. الموديول بيستخدم `writes_product`
  بدل `writes_core`.
- **ملزمة:** أي تشغيلة بعد كده عن نفس المنتج (سكريبت، UGC، كوبي) بتقول اللي لازم يتقال
  وما بتقولش الممنوعات (قاعدة 8 في `OPERATING_RULES`).
- **المراجعات بتراجع على أساسها:** بند «التزام بالإرشادات» بيتضاف للتقييم، وأي ممنوع اتقال
  بيبقى أول خطأ.
- **بتتبعت مع المنتج المختار بس**، مش مع كل تشغيلة.
- **Brand Brain:** علامة «إرشادات معتمدة» جنب المنتج، وقسم لوحده تفتحها أو تمسحها منه
  (الـ admin بس). لو مسحت المنتج، إرشاداته بتتمسح معاه.

**الخطوات:** تختار المنتج ← تشغّل ← **تعتمد** (admin) ← الإرشادات بتدخل الـ Brain.

### قرارات التصميم
| القرار | السبب |
|---|---|
| مفيش عمود جديد في جدول المنتجات | التول مافيهاش migrations (`create_all` بس)، والعمود الجديد مش هيتضاف للجدول الموجود على Railway، فالموقع كله كان هيقع |
| الإرشادات مقسّمة بالـ id مش بالاسم | لو اسم المنتج اتغيّر بعد الاعتماد، الإرشادات بتفضل مربوطة بيه |
| إرشادات المنتج المختار بس في كل تشغيلة | في الأول كانت إرشادات كل المنتجات بتتبعت. مع كتالوج كبير من EasyOrders ده كان هيزوّد التوكنز في كل تشغيلة، حتى في الخطة التسويقية |
| اسم المنتج بيتطبّع عند التشغيل | عشان التشغيل والاعتماد يقارنوا نفس الاسم بالظبط |
| المنتج بيتأكد منه قبل الاعتماد | لو المنتج اتمسح أو اسمه اتغيّر، الاعتماد بيرفض (409) والمخرج بيفضل مسودة، من غير ما يتغيّر أي حاجة |

### التحقق
- **62 اختبار ناجح** (55 قديمة + 7 جداد)، وكل اختبار جديد اتجرب بإرجاع الباج اللي بيحمي منه.
- **أول نسخة من الاختبارات ماكانتش بتمسك تسريب الإرشادات لقسم الاستراتيچية**، لأن الإرشادات
  كانت المفتاح الوحيد في الـ Brain فالقسم ده مكانش بيظهر أصلًا. اتقوّى الاختبار بإضافة Positioning
  معتمد جنبها.
- **في المتصفح:** الكارت أول واحد وأيقونته صح، والحقول والمنتجات في الفورم، والإرشادات ظاهرة
  تحت المنتج في الـ Brand Brain، وصفر أخطاء JS.
- **ماتجربش:** تشغيلة حقيقية بالموديل (مفيش مفتاح API في بيئة الاختبار). شكل البريف الفعلي
  هيبان أول تشغيلة على Railway.

## 14. تحديث: مخرجات الكتابة ماكانتش بتبيع

### المشكلة
موديول الـ UGC Scripts اتجرب على براند ERASE (سبراي إزالة روائح، 349 جنيه، 13 أفاتار في
الـ Brain، وSTPD معتمد). المخرج كان مكتوب كويس وشكله طبيعي، **لكنه ماكانش بيحث على الشراء.**

**الأدلة من المخرج نفسه:**
- **الـ CTA** في التلات سكريبتات كان «اللينك تحت، جربوها». مفيش سعر، ولا سبب تشتري دلوقتي.
- **اعتراضات السعر** مكتوبة حرفيًا في الأفاتارات ومحدش ردّ عليها: «349 + 60 شحن كتير على طالب»،
  و«المعطر المعلق بـ 30 جنيه».
- **الاعتراض الأساسي** «هو مجرد معطّر ولا بيعالج الريحة؟» اتلمس بشكل ضعيف.
- **أقوى زوايا البيع اتهملت:** سواق الأوبر اللي الريحة بتنزّل تقييمه ودخله، وصاحب الـ Airbnb اللي
  بتجيله ريفيوهات 3 نجوم.
- **التلات سكريبتات لكرييتور واحد عام** (أم شابة 28 سنة)، رغم إن فيه 13 أفاتار.
- **الهوكات عامة:** «يا جماعة كنت هقع من اللي حصلي»، و«الحاجة الوحيدة اللي غيرت حياتي».
- **الإثبات مايع:** «حسيت إن الريحة راحت».
- **صفحة كاملة افتراضات** قبل أول سكريبت.

### التشخيص: الخلل في الموديول مش في البيانات
الـ Brain والـ STPD كانوا قويين ومحددين، والسكريبتات استخدمتهم فعلًا (نور، والقطط، والـ SKUs، وآلية
Dual-Erase). الأسباب الحقيقية:

| # | السبب |
|---|---|
| 1 | التعليمات كانت بتطلب كلام «طبيعي» بس، ومفيهاش أي حاجة عن البيع |
| 2 | الموديول ماكانش بيحمّل `selling-elements.md` (عناصر البيع الـ 18، وCialdini، ومصفوفة الاعتراضات). كان بيحمّل بدله `questioning-flows.md` (أسئلة التعارف)، ومالوش لازمة بعد ما التعارف اتجاوب |
| 3 | مفيش حقل للأفاتار ولا للعرض، فالموديل رجع لكرييتور عام |
| 4 | الحذر في القواعد العامة كان بيحوّل الادعاء اللي مش مثبت لكلام مايع، بدل ما يحوّله لتجربة تتصور |
| 5 | الموديول كان شغال على Sonnet (الموديل السريع) |

### الإصلاح
**موديول الـ UGC اتبنى من جديد:**
- بقى على **Opus**، وبيحمّل `selling-elements` و`frameworks` و`power-elements` جنب `hooks`
  و`creative-formats`.
- **كل سكريبت لأفاتار مختلف من الـ Brain**، ولو اخترت أفاتار معيّن بيطلّع 3 زوايا ليه. وكل سكريبت
  بمرحلة وعي مختلفة.
- **كل سكريبت لازم يمشي في الكلام نفسه بالترتيب ده:** الهوك من كلام الأفاتار ← تكلفة المشكلة عليه
  ← الاعتراض يتقال ويترد عليه ← تجربة قدام الكاميرا ← السعر مقارنة بتكلفة المشكلة ← CTA فيه سبب
  حقيقي للشراء دلوقتي.
- **في الآخر ترتيب للسكريبتات حسب التحويل المتوقع**، وكل سكريبت معاه ملاحظة كاستينج (مين يقدر
  يصوّره بصدق).
- **حقول جديدة:** «الأفاتار المستهدف» (قايمة من أفاتارات الـ Brain) و«العرض والسعر».

**معيار بيع موحّد (`_CONVERSION_BAR`)** على كل موديول هدفه البيع: UGC وVideo Ad Script وAd Copy
وVoiceover وLanding Copy وEmail & SMS. المعيار بيتحط في الطلب نفسه، فبيبقى ليه الأولوية على القواعد
العامة. وبيطلب:
1. الهوك من لحظة الأفاتار بكلامه هو، من غير بدايات عامة
2. تكلفة المشكلة واضحة على الأفاتار ده
3. الاعتراض الأساسي يتقال ويترد عليه
4. الآلية تتعرض بتجربة تتصور أو تتخيل
5. إثبات حقيقي بس: تجربة، أو ريفيو من الـ Brain، أو معلومة متقدّمة
6. السعر مقارنة بتكلفة المشكلة أو البديل، بأسعار حقيقية بس
7. CTA واحد فيه سبب حقيقي للشراء دلوقتي، من غير ندرة أو خصم مخترع

ومعاه قاعدة إن **الحذر مايخليش الكوبي مايع:** الادعاء اللي مش مثبت يتبدّل بتجربة محددة تتصور، مش
بكلام عام. والافتراضات بقت في **آخر** المخرج، في 4 نقط بالكتير. إرشادات المنتج والممنوعات لسه ملزمة.

**تعديلات تانية:** Ad Script وVoiceover بقوا يحمّلوا `selling-elements`، وAd Script وAd Copy اتضافلهم
حقل الأفاتار. موديولات المراجعة ماتغيرتش.

### التكلفة
تشغيلة الـ UGC بقت تكلّف حوالي **مرتين ونص** قد الأول، لأنها اتنقلت من Sonnet لـ Opus. وتقدر ترجع
لـ Sonnet في أي تشغيلة من قايمة الموديل في الفورم.

### التحقق
- **65 اختبار ناجح** (3 منهم جداد). الاختبارات الجديدة بتأكد على **البرومبت اللي بيوصل للموديل
  فعلًا**: إنه على Opus، وفيه مرجع البيع، وفيه المعيار، وفيه الأفاتار المختار. ولما رجّعت الإعدادات
  القديمة مؤقتًا، الاختبارات التلاتة فشلت.
- **في المتصفح:** قايمة الأفاتارات بتعرض أفاتارات الـ Brain، وحقل العرض ظاهر، والموديل الافتراضي
  Opus، ومفيش أخطاء JS.
- **ماتجربش:** شكل المخرج الجديد نفسه، لأن مفيش مفتاح API في بيئة الاختبار. محتاج تشغيلة حقيقية على
  Railway ومقارنتها بالمخرج القديم (القسم 11).

## 15. تحديث: أكتر من أفاتار، ومخرج معتمد كمرجع، وتعديل المخرج بطلب

### أ. اختيار أكتر من أفاتار (كوميت `486e21c`)
**الطلب:** حقل الأفاتار المستهدف كان بيقبل اختيار واحد بس. المطلوب أكتر من اختيار، ويبقى ده الشكل
العام في كل الأدوات اللي فيها أفاتار.

**اللي اتعمل:**
- حقل واحد موحّد بيتشارك فيه **11 موديول**: Angle Generator، وHooks، وVideo Ad Script، وUGC،
  وVoiceover، وLanding Copy، وAd Copy، وEmail & SMS، والتلات مراجعات.
- بتختار من أفاتارات الـ Brain **لحد 6**. فيه عدّاد «اخترت N من 6» وزرار «مسح»، والباقي بيتقفل لما
  توصل للحد. لو الـ Brain فاضي، الحقل بيرجع نص عادي.
- **في البرومبت:** الأسامي بتتبعت مفصولة بفواصل (مش JSON). ولو اخترت أكتر من واحد، أدوات الكتابة
  بتدّي كل أفاتار هوك واعتراض ودليل خاص بيه، والمراجعات بتدّي كل أفاتار درجة ملاءمة لوحده.
- **UGC:** سكريبت لكل أفاتار مختار، أو 3 زوايا لو اخترت واحد، أو 3 سكريبتات لأفاتارات مختلفة لو
  ماختارتش.

**حماية على السيرفر:** الاختيار بيتنضّف (مسافات وتكرار)، وبيترفض لو فيه أكتر من 6، أو أفاتار مش في
الـ Brain، أو قيمة مش نص. والتشغيلات القديمة اللي فيها أفاتار واحد كنص لسه شغالة. ولو القايمة فاضية،
المساعد الذكي بيعتبرها حقل فاضي يقدر يملاه.

### ب. مخرج معتمد كمرجع (كوميت `65126e0`)
**السؤال:** هل المخرجات المعتمدة في المكتبة بتتشاف لما نطلّع شغل جديد؟

**الإجابة كانت:** لأ. اللي بيوصل للموديل هو الـ Brand Brain بس (والمخرجات اللي بتكتب فيه بعد
الاعتماد، القسم 12). المكتبة نفسها مابتتقريش، وده متعمّد: لو اتبعتت كلها، التكلفة بتزيد والموديل بيقلّد
مخرجات مالهاش علاقة بالمهمة.

**الحل:** اختيار صريح. في أي فورم فيه «استخدم مخرج معتمد كمرجع»، تختار منه **لحد 3** مخرجات
معتمدة، وبيتبعتوا للموديل كمراجع للتشغيلة دي بس. وفي نافذة المخرج بيظهر «اتبنى على: …».

**الحماية:**
- مش بيظهر في الاختيار غير المخرجات **المعتمدة والمكتملة** من **نفس البراند** (مش الأقسام الفرعية).
  وده بيتأكد منه السيرفر تاني وقت إنشاء التشغيلة، مش الواجهة بس.
- لو مجموع حجم المراجع عدّى 120 ألف حرف، الطلب **بيترفض برسالة**، مش بيتقصّ من غير ما تعرف.
- لو مرجع اتشال اعتماده بين الإنشاء والتشغيل، بيتشال من المراجع وبتظهر رسالة.
- المفتاح الداخلي اللي بيتخزن فيه المراجع بيحطه السيرفر بس، والعميل مايقدرش يبعته بنفسه.
- مسار «الحملات» كمان بيبعت المراجع.

### ج. تعديل المخرج بطلب (كوميت `9a93103`)
**الطلب:** لما المخرج مايعجبنيش أو عايز أظبط تنسيقه أو أعدّل حاجة معيّنة، كنت بضطر أعيد التشغيلة من
الأول بتغيير المدخلات. المطلوب خانة prompt في نافذة المخرج تعدّل المخرج ده على قد الطلب.

**إزاي بيشتغل:**
- تحت المخرج فيه خانة **«عدّل المخرج ده بطلب»**. بتكتب اللي عايزه (مثلًا «خلّي الجدول 3 أعمدة،
  واختصر كل هوك لسطر، وخلّي الـ CTA أقوى») وتدوس «عدّل».
- النص الجديد بيظهر وهو بيتكتب، مكان المخرج القديم.
- الموديل بيشوف نفس اللي شافه التشغيل الأصلي: الـ skill، والـ Brand Brain، وإرشادات المنتج المختار،
  والمراجع المعتمدة. والتعليمات: **نفّذ المطلوب بالظبط، وسيب الباقي زي ما هو، ورجّع المخرج كامل.**
  ولو حاجة ماينفعش تتنفذ، بيكتب سطر «⚠️ ملاحظة:» في الآخر.
- التكلفة بتتسجل في الاستخدام كعملية `text_revision`.

**النسخة الأصلية مابتضيعش:**
- التعديل بيتحفظ كـ **نسخة جديدة «مسودة»**، والقديمة بتروح «مقارنة النسخ والرجوع» بملاحظة «قبل
  التعديل بالـ AI: …» وتقدر ترجعلها بضغطة.
- لو المخرج كان معتمد، الاعتماد مابيتنقلش للنسخة الجديدة، ولازم يتعتمد تاني (وده اللي بيحدّث الـ Brain).
- المراجعات (اللي ليها سكور) السكور بتاعها بيتحسب من جديد من النسخة المعدّلة.

**الحماية — التعديل مابيتحفظش والأصل بيفضل زي ما هو لو:**
| الحالة | ليه |
|---|---|
| الرد اتقطع قبل ما يخلص (`max_tokens`) | عشان مخرج ناقص مايحلّش محل مخرج كامل |
| الرد رجع فاضي | — |
| علامات أقسام الخطة اتغيّرت | الخطط الكاملة متقسّمة أقسام، ولو اتدمجت أو اتشالت، إعادة توليد قسم والتصدير بيبوظوا |

وفي الحالات دي بتظهر رسالة بالسبب، والتوكنز اللي اتصرفت بتتسجل برضه.

**وهو بيتعدّل** (حالة جديدة اسمها `revising` وبتظهر في المكتبة «بيتعدّل»): التحرير اليدوي، وتغيير
حالة الاعتماد، والحذف، وتعديل تاني، كلهم بيترفضوا. ولو السيرفر عمل restart في النص، المخرج بيرجع
«تم» بالنسخة الأصلية. والتعديل بيتطلب برقم النسخة اللي قدامك، فلو حد تاني عدّل قبلك الطلب بيترفض.
ومايتعملش على قسم فرعي (القسم ليه إعادة التوليد بتاعته) ولا على مخرج لسه شغال.
